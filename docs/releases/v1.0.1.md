# overnight v1.0.1

Released 2026-09-06. Requires Python 3.9+, `pyyaml`, git and the Claude Code CLI
on the PATH. Install with `python install.py`; upgrade by pulling this checkout,
because the install is a link and not a copy.

This release is about two things: **what an unattended worker is allowed to
reach**, and **what a night of unattended work actually costs you**. No spec
format, step id, gate form or `overnight/` path has changed, so a plan written
against v1.0.0 runs unmodified.

## An unattended worker can no longer act outside the tree

The whole safety argument of this runner is that git is the undo: a failed gate
resets, a bad review reverts, a stray file is quarantined rather than deleted.
That argument only holds for things that happen *inside the repository*.

A worker was previously handed the full tool set, which on a current CLI includes
tools that publish a page, schedule or fire work that outlives the run, message
somebody, or fan out further agents. None of that is reachable by a reset, and
nobody is awake to notice it happening at 3am.

So `UNATTENDED_DENY` now denies `Artifact`, `CronCreate`, `CronDelete`,
`CronList`, `DesignSync`, `PushNotification`, `RemoteTrigger`, `SendMessage` and
`Workflow` to every worker kind - build, review, reflect and diagnostic alike.
The review step's existing `Edit`/`Write`/`NotebookEdit` fence is unchanged and
now sits on top of that list, passed as a single `--disallowedTools` rather than
two (passing the flag twice left it to the CLI to decide which list won, which is
not a thing a runner should be relying on). A tool name your installed CLI does
not have is simply inert, so the list can safely name one that only some versions
ship.

Their definitions leaving the prefix is worth roughly 4% of a run's tokens. That
is a bonus. The reason is the reset.

**If you are upgrading:** a brief that told a worker to use any of those tools
will now fail. Nothing else in your plan is affected.

## You can now see what the run spent on not building

`docs/token-efficiency.md` measured 14 real workers against 22 interactive
sessions as a control, and the headline is not what we expected: a headless
worker costs *the same per API call* as a person working interactively. The risk
of an overnight run costing multiples of the same work done by hand is not
per-call inefficiency. It is structural - the reviews, the reflects, the reworks
and the discarded attempts. On the first real run those were 26% of the bill.

`SUMMARY.md` now says so, under the cost total:

    Cumulative worker cost over every step this plan has run, not just this session (self-reported): $18.40
    Of that, **$4.85 (26%) was not building**: review and reflect steps, and the rework they ordered. Build steps $13.55, of which 2 needed more than one attempt and 1 was reworked after a review - that spend is inside the build figure, because the ledger keeps one cost per step.

Read the two halves differently. The kind split is exact. The retried and
reworked counts are indicative, because the ledger keeps one cost per step, so a
step's discarded attempts hide inside its own figure.

A high overhead share is not automatically bad - a review that catches a real bug
has earned its money. But a run where half the spend is not building is a run
whose plan is asking the wrong questions, and now you find that out over coffee
rather than never.

## Fixed: a rework's cost never reached the ledger

Writing that split exposed a real defect. `run_build` charges its workers to the
step it is building - but a rework rebuilds a step that was recorded long before,
and whose cost was flushed to the ledger when it was recorded. The rework's spend
therefore sat in memory until the process exited and appeared nowhere: not in
`SUMMARY.md`, not in any `--mode` total.

**Every run before this release under-reports itself by whatever its reworks
cost.** If you have quoted a figure from an earlier `SUMMARY.md`, it was low.

The cost is now attributed to the review step that ordered the rework, which is
also where it belongs when you are reading the overhead split - so a review
step's `cost_usd` can legitimately exceed what its own reviewing worker spent.

The guard added for it is the invariant rather than the symptom: the ledger total
must equal what the worker logs say was spent, whatever path spawned them. It was
shown to fail against the unfixed runner (`ledger $0.10 vs logs $0.11`) before
the fix went in.

## Workers are now told what a tool result costs

Context re-reads are 56% of a run's spend, and the reason is that a tool result
is paid for when it arrives and again on every call after it - a 50 KB file read
at turn 3 of a 40-turn step is charged 38 more times.

Every brief now says so, and asks for the habits that follow: Grep to locate
before you Read, `offset`/`limit` on a large file, do not re-read what is already
in context, filter a noisy command rather than dumping it. Alongside that, the
existing nudge toward `Read`/`Grep`/`Glob` over `cat` and `sed` for exploration,
with Bash reserved for the test suite, build scripts and git.

Nothing is forbidden - Bash stays fully available - and this is a change to what
a worker reaches for first, not to what it can do. Whether it moves the 56% is
not yet measured; the next real run is the first test of it.

## Also

- README section 12's permission table said reflect and diagnostic workers ran
  under `acceptEdits`. They have run under `bypassPermissions` since before
  v1.0.0 was cut - a reflect must be able to do more than edit and commit, and a
  diagnostic must be able to run the failing test it exists to explain. The
  documentation had simply never caught up.
- `tools/tally.py` splits a session's spend into its buckets and lists the tool
  results that filled the context, for a run directory or a single transcript.
  It reconciles exactly with the CLI's own reported total.

## Upgrading

    git pull
    python install.py --check     # confirm the skill still points at this checkout
    python selftest.py            # must print SELFTEST PASS before any launch

The install is a directory junction (Windows) or a symlink (elsewhere), so a pull
is the upgrade. If `--check` reports "a real directory", something replaced the
link with a copy at some point and your fixes were not reaching the skill:
`python install.py --force` repairs it.

Full detail in `CHANGELOG.md`; the measurements behind the cost claims are in
`docs/token-efficiency.md`.
